# Translating Start From Nowhere

The question this answers: what does it actually take to serve this site in a
language other than English, and what should we do first. Numbers here come from
`python3 src/i18n_audit.py`, which reads the built pages rather than the
templates, so it counts what a reader sees. Re-run it before trusting them.

## What the Audit Says Today

| Bucket | Strings | Reachable by machine translation? |
|---|---|---|
| Markup text nodes | 954 | Yes, today |
| Visible attributes (title, placeholder, aria-label, alt, meta description) | 264 | Yes, today |
| UI copy inside inline scripts | 1,270 | No |
| Generated data payloads (question banks, school table) | 5,209 | No, and this is editorial, not engineering |

Roughly 19,800 words of UI copy across the site.

The number that decides the plan is the split inside that third row. Of the
1,270 script strings, **1,099 are in the two trainers** and only about 171 are
in the whole content site (landing, rankings, school pages, international
guide, checklist, exam guides, pricing, blog, forum). Translating the content
site is a small job. Translating the trainers is most of the work.

## The Staged Plan

### Stage 0: Do Not Block Translation (done, keep it that way)

Every page is server-rendered static HTML with a real `<html lang="en">`. That
means Chrome's built-in translation, Google Translate, and the translation
layers inside search results already work on the content site right now. This
is worth protecting:

- Never move body copy into JavaScript. Text that is written into the DOM by a
  script is invisible to every one of those tools.
- Never bake copy into an image or an inline SVG.
- Keep `lang` accurate. If we ever publish a translated page, its `lang` must
  change with it, or translation tools will not offer to translate it.

A reader in Tokyo or Mumbai can already read the international guide in their
own language via the browser. That is not as good as a real translation, but it
is not nothing, and it costs us zero.

### Stage 1: Externalize the Content-Site Strings (the small job)

Introduce `src/i18n/en.json`, a flat catalog of message id to English string.
Templates keep English as the default so nothing changes visually on day one:

```
{{t:apply.hero.title}}     in a template
t('apply.hero.title')      in an inline script
```

`partials.py` gains a `translate(html, locale)` that substitutes `{{t:...}}`
at build time and injects the matching JSON catalog for the script side. The
build loops over locales and writes one tree per locale. Missing keys fall back
to English and print a build warning, never a blank.

Scope: about 1,390 strings (markup, attributes, and the 171 content-site script
strings). This is the stage that ships a genuinely Spanish or Hindi version of
the rankings, the international guide and the checklist.

### Stage 2: URL Scheme and Routing

Path prefix, not subdomain, not query string:

```
/schools/            English, canonical
/es/schools/         Spanish
/hi/schools/         Hindi
```

Path prefix keeps one domain's authority, is what Google documents as the
clearest signal, and needs no DNS or certificate work on Cloudflare.

Each page then carries reciprocal alternates, every locale pointing at every
other including itself, plus `x-default` on the English page:

```
<link rel="alternate" hreflang="en" href="https://startfromnowhere.com/schools/">
<link rel="alternate" hreflang="es" href="https://startfromnowhere.com/es/schools/">
<link rel="alternate" hreflang="x-default" href="https://startfromnowhere.com/schools/">
```

`partials.py` should emit these from the locale list so they can never drift
out of sync with what was actually built, and `build_blog.py` should emit one
sitemap entry per locale per page.

Worker routing: read `Accept-Language` on a request to a path with no locale
prefix and **offer** the translated page with a dismissible banner rather than
redirecting. A hard redirect on `Accept-Language` traps anyone whose browser
language is not the language they read in, which is extremely common among the
exact audience this is for. If we ever do redirect, set an override cookie on
the first manual language switch and never redirect again for that reader.

### Stage 3: The Trainers (the large job)

1,099 script strings across the GMAT and SAT apps. Both render from one
template, so the work is done once and lands twice. Do this only after Stage 1
proves that translated pages actually earn traffic and signups, because it is
the single largest chunk of work in the plan.

### Stage 4: Content, Which Is Not an Engineering Problem

The 5,209 data strings are question stems, answer choices, explanations, and
school class-profile notes. Two hard constraints:

- **Never machine-translate a sourced fact.** A visa rule, a score, or a
  deadline rendered wrong in Hindi is worse than the same rule in English,
  because the reader cannot tell it is wrong. Anything carrying a source, a
  year and a URL either gets a human translator or stays in English.
- **Never machine-translate a verbal question.** A GMAT Verbal or SAT Reading
  and Writing item is a test of English. Translating it destroys the item.
  Quant and Data Insights items translate; verbal items do not, and should be
  marked as such in the bank rather than handled by convention.

## Which Languages, and the Honest Case for Waiting

The site's own analytics over its first month, which is all the history there
is, show 124 sessions, 95 of them from the United States. India is the second
country at 5 sessions. There is not yet a traffic case for any specific
language, and picking one from a month of data at this volume would be guessing.

What the data does support: the pages people outside the United States land on
are `/schools/` and the blog, almost entirely from organic search. So when we
do translate, those are the pages to translate first, and Stage 1 is scoped to
exactly them.

The trigger to start Stage 1 should be a measurement, not a hunch. The cheapest
one available: Google Search Console impressions by country, once the property
has enough history. When a non-English-speaking country produces real
impressions on `/schools/` or the guides, translate for that country. Until
then, Stage 0 is genuinely the right amount of work, and the audit script is
here so the decision can be re-costed in seconds whenever that changes.

## Accessibility, Which Is the Other Half of the Question

"Accessible in other languages" and "accessible" are different asks and both
matter. The current state, and what to fix:

- Every page has one `h1` and a sensible heading order.
- Visible attributes are audited above, which means `alt` and `aria-label`
  coverage is measurable rather than assumed.
- Colour is never the only carrier of meaning in the rankings table: the
  acceptance-rate colouring is a hint on top of the number, not instead of it.
- Open item: a full keyboard-only pass through the trainer and the checklist,
  and a screen reader pass on the rankings table. Neither has been done.
